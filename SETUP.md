# SETUP.md — развёртывание на Amvera Cloud

Система полностью работает **локально без единого внешнего аккаунта**: хранилище — папка
на диске, бэкап — папка на диске, Telegram — вывод в консоль. Этот документ нужен только
для выкатки в облако.

Порядок важен: каждый следующий шаг опирается на предыдущий.

---

## Хорошая новость: на Amvera внешние сервисы почти не нужны

У Amvera есть **постоянный диск `/data`**, который переживает пересборки. Значит локальные
провайдеры — не только для разработки: медиа и бэкапы лежат на этом диске и никуда не деваются.

| Что | Локально | На Amvera | Внешний аккаунт |
|---|---|---|---|
| Хранилище медиа | папка `./storage` | папка `/data/storage` | **не нужен** |
| Бэкапы | папка `./backups` | папка `/data/backups` | **не нужен** |
| База данных | Postgres в Docker | управляемый PostgreSQL Amvera | не нужен |
| TLS и домены | — | Amvera выдаёт сама | не нужен |
| Уведомления | в лог сервера | в лог, либо Telegram-бот | по желанию |

Cloudflare, R2 и Google Drive из плана на Amvera **не обязательны**. Разделы про них
оставлены в конце — на случай, если позже понадобится CDN или бэкап вне площадки.

---

# ⚠️ ЧЕТЫРЕ ЛОВУШКИ AMVERA

**Прочитайте до того, как создавать проекты.** Каждая стоит вечера отладки.

> ## 1. Переменные окружения НЕ доступны на этапе сборки
>
> В документации Amvera прямо сказано: «На этапе сборки переменные окружения не доступны».
>
> **Чем это бьёт именно нас.** Адрес API вшивается в JS-бандл при сборке:
> `NEXT_PUBLIC_API_URL` у сайта и `VITE_API_URL` у админки. Задать их в разделе
> «Переменные» **бесполезно** — сборка их не увидит, и фронтенд пойдёт стучаться
> в `localhost:3001` прямо из браузера пользователя.
>
> **Что делать.** Вписать адрес API прямо в `Dockerfile` до первого пуша.
> Место помечено комментарием «ВНИМАНИЕ» в двух файлах:
> - `web/Dockerfile` → `ARG NEXT_PUBLIC_API_URL=...`
> - `admin/Dockerfile` → `ARG VITE_API_URL=...`
>
> Это не секрет, а публичный адрес — держать его в репозитории нормально.
> Все остальные переменные (пароли, токены, строка подключения к БД) задаются
> в «Переменных» как обычно: они нужны только в рантайме.

> ## 2. Один Amvera-проект — один сервис. Никакого docker-compose
>
> У нас четыре части: база, backend, сайт, админка. На Amvera это **четыре отдельных
> проекта**, а не один `docker compose up`. `docker-compose.yml` из репозитория
> на Amvera не используется вовсе — он остаётся для запуска на своём VPS.
>
> Каждый проект — свой git-репозиторий Amvera. Пушим туда **поддеревом**, чтобы корнем
> оказалась нужная папка (в ней уже лежат `Dockerfile` и `amvera.yml`):
>
> ```bash
> git subtree push --prefix backend amvera-api master
> ```

> ## 3. Куки не ходят между поддоменами `*.amvera.io`
>
> Бесплатные домены выглядят как `pai-web-ник.amvera.io` и `pai-api-ник.amvera.io`.
> Кука авторизации, выставленная API, привязана к своему хосту и на домен сайта
> **не попадает**. Middleware сайта её не увидит и будет вечно кидать на `/login`.
>
> Расширить куку на `.amvera.io` нельзя: она утекла бы во все чужие проекты площадки.
>
> **Что делать:** взять свой домен (шаг 6). Тогда сайт и API — соседние поддомены
> одного домена, `COOKIE_DOMAIN=.вашдомен.ru`, и всё работает ровно как задумано.
> Домен в зоне `.ru` стоит около 1000 ₽ в год — это дешевле вечера отладки.
>
> Админка на бесплатных доменах работает и без своего домена: она обращается к API
> кросс-доменно с `credentials: 'include'`, и браузер шлёт куку самого API. Проблема
> только у публичного сайта, потому что он проверяет куку на своей стороне.

> ## 4. Версия pg_dump должна совпадать с версией PostgreSQL
>
> В образе backend стоит `postgresql16-client`. Если управляемый кластер Amvera окажется
> новее 16-й версии, `pg_dump` откажется работать с ошибкой про несовпадение версий.
>
> Молчаливой поломки не будет: бэкап сам переключится на логический дамп средствами
> Node (NDJSON) и продолжит работать — в логе прогона будет видно `method: ndjson`.
> Но если хочется именно `pg_dump`, поправьте версию клиента в `backend/Dockerfile`
> под ту, что показывает Amvera на странице кластера.

## Шаг 1. Аккаунт и оплата — 10 минут

1. Зарегистрироваться: [amvera.ru](https://amvera.ru/).
2. Пополнить баланс. Ориентир по тарифам: управляемый PostgreSQL — от ~290 ₽/мес,
   приложения — от ~170 ₽/мес каждое. На нашу конфигурацию (база + три сервиса)
   закладывайте примерно 900–1500 ₽/мес.
3. Запомнить свой ник — он входит во все внутренние имена хостов.

## Шаг 2. База данных — 15 минут

1. На главной выбрать **PostgreSQL** → «Создать базу данных».
2. Название проекта: `pai-db`. Тариф — не ниже «Начального».
3. Заполнить:
   - имя базы: `pai`
   - пользователь: `pai` (имя `postgres` занято платформой)
   - пароль: сгенерировать длинный и положить в менеджер паролей
   - число реплик: 1 достаточно
4. Дождаться статуса «PostgreSQL запущен».
5. На странице кластера найти **внутреннее доменное имя**. Формат:

   ```
   amvera-<ваш-ник>-cnpg-pai-db-rw
   ```

   Суффиксы: `-rw` — чтение и запись (нужен нам), `-ro` — только чтение с реплики,
   `-r` — чтение с любого узла.

6. Собрать строку подключения — понадобится на шаге 4:

   ```
   postgresql://pai:<пароль>@amvera-<ник>-cnpg-pai-db-rw:5432/pai
   ```

> Наружу база по умолчанию не смотрит, и это правильно. Если нужен доступ
> из DBeaver, на странице кластера отдельно создаётся домен типа POSTGRES с SSL.

## Шаг 3. Создать три проекта приложений — 10 минут

Создайте три проекта типа «Приложение», окружение — **Docker**:

| Проект | Что это | Порт внутри |
|---|---|---|
| `pai-api` | backend | 3001 |
| `pai-web` | публичный сайт | 3000 |
| `pai-admin` | админка | 80 |

Порты уже прописаны в `amvera.yml` внутри каждой папки репозитория — трогать не нужно.
Проекту `pai-api` на вкладке хранилища включите **постоянный диск**: в нём будут жить
медиа и бэкапы.

## Шаг 4. Переменные окружения — 20 минут

Переменные задаются в разделе **«Переменные»** каждого проекта. Пароли и токены
добавляйте как **секреты** — они хранятся в отдельном хранилище, а не в базе платформы.

Сначала сгенерируйте два секрета:

```bash
openssl rand -hex 32   # → JWT_SECRET
openssl rand -hex 32   # → REVALIDATE_SECRET
```

### Проект `pai-api`

| Переменная | Значение | Тип |
|---|---|---|
| `DATABASE_URL` | строка подключения из шага 2 | секрет |
| `NODE_ENV` | `production` | переменная |
| `JWT_SECRET` | первый сгенерированный | секрет |
| `REVALIDATE_SECRET` | второй сгенерированный | секрет |
| `ADMIN_LOGIN` | ваш логин администратора | переменная |
| `ADMIN_PASSWORD` | нормальный пароль, не `admin12345` | секрет |
| `ADMIN_NAME` | ваше имя | переменная |
| `COOKIE_SECURE` | `true` | переменная |
| `COOKIE_DOMAIN` | `.вашдомен.ru` (со своим доменом) или пусто | переменная |
| `CORS_ORIGINS` | адреса сайта и админки через запятую | переменная |
| `PUBLIC_WEB_URL` | адрес сайта | переменная |
| `PUBLIC_ADMIN_URL` | адрес админки | переменная |
| `WEB_INTERNAL_URL` | `http://amvera-pai-web-run-<ник>` | переменная |
| `STORAGE_LOCAL_DIR` | `/data/storage` | переменная |
| `STORAGE_LOCAL_PUBLIC_URL` | `https://<адрес API>/media` | переменная |
| `BACKUP_LOCAL_DIR` | `/data/backups` | переменная |

Обратите внимание на формат внутреннего имени приложения — он **отличается** от формата
у базы: у приложений это `amvera-<проект>-run-<ник>`, у базы `amvera-<ник>-cnpg-<проект>-rw`.
Перепутать эти два порядка — самая частая причина «не могу подключиться».

### Проект `pai-web`

| Переменная | Значение |
|---|---|
| `NODE_ENV` | `production` |
| `JWT_SECRET` | **тот же**, что у API — middleware проверяет подпись куки |
| `REVALIDATE_SECRET` | тот же, что у API |
| `API_INTERNAL_URL` | `http://amvera-pai-api-run-<ник>` |

### Проект `pai-admin`

Переменные не нужны: это статика, адрес API уже вшит при сборке.

## Шаг 5. Вписать адреса API в Dockerfile — 5 минут

Это **ловушка 1**. До первого пуша откройте два файла и подставьте адрес API:

```dockerfile
# web/Dockerfile
ARG NEXT_PUBLIC_API_URL=https://pai-api-ваш-ник.amvera.io

# admin/Dockerfile
ARG VITE_API_URL=https://pai-api-ваш-ник.amvera.io
```

Со своим доменом (шаг 6) — соответственно `https://api.вашдомен.ru`.

Закоммитьте изменение: оно должно уехать вместе с кодом.

## Шаг 6. Свой домен — 30 минут, но по факту обязательно

Из-за **ловушки 3** публичный сайт на бесплатных доменах не пустит никого дальше `/login`.

1. Купить домен (любой регистратор).
2. В настройках каждого проекта Amvera: «Добавить домен».
3. Прописать у регистратора DNS-записи, которые покажет Amvera:

   | Поддомен | Проект |
   |---|---|
   | `pai.вашдомен.ru` | `pai-web` |
   | `api.pai.вашдомен.ru` | `pai-api` |
   | `admin.pai.вашдомен.ru` | `pai-admin` |

4. Дождаться выпуска сертификатов — Amvera делает это сама.
5. Проверить, что все переменные из шага 4 и `ARG` из шага 5 указывают на новые адреса.
   `COOKIE_DOMAIN` теперь `.pai.вашдомен.ru`.

## Шаг 7. Первый деплой — 15 минут

Каждый сервис пушится своим поддеревом. Ник и имена проектов подставьте свои:

```bash
git remote add amvera-api   https://git.amvera.ru/<ник>/pai-api
git remote add amvera-web   https://git.amvera.ru/<ник>/pai-web
git remote add amvera-admin https://git.amvera.ru/<ник>/pai-admin
```

```bash
git subtree push --prefix backend amvera-api master
git subtree push --prefix web     amvera-web master
git subtree push --prefix admin   amvera-admin master
```

Логин и пароль — от аккаунта Amvera. Сборка стартует сама; следить за ней
на вкладках «Лог сборки» и «Лог приложения».

Порядок важен: сначала `pai-api` (он накатывает миграции и создаёт администратора),
затем остальные.

> **Если ветка называется `main`, а Amvera ждёт `master`** — `git subtree push` уже
> отправляет в `master`, так что здесь ничего делать не нужно. Для обычного `git push`
> формат был бы `git push amvera main:master`.

## Шаг 8. Проверка — 15 минут

По порядку:

- [ ] `https://<адрес API>/health` → `{"ok":true,"db":true,"storage":true}`
- [ ] Админка открывается и пускает по логину и паролю из `ADMIN_PASSWORD`
- [ ] Загрузка картинки в медиа-библиотеку доходит до статуса READY
- [ ] Картинка отдаётся по своему адресу и переживает **пересборку проекта**
      (это проверка того, что постоянный диск подключён)
- [ ] Публикация гайда → он виден на публичном сайте
- [ ] Без входа сайт редиректит на `/login`
- [ ] В разделе «Бэкапы» кнопка «Полный» отрабатывает зелёным
- [ ] В логе прогона видно, каким способом сделан дамп: `pg_dump` или `ndjson`

Проверку постоянного диска не пропускайте: если его забыли включить, всё будет
работать ровно до первой пересборки, а потом медиа исчезнут.

## Обновление после первого деплоя

```bash
git subtree push --prefix backend amvera-api master
```

Пушьте только те поддеревья, где менялся код. Если правили `web/Dockerfile`
или `admin/Dockerfile` (адрес API) — нужен пуш соответствующего сервиса.

> `git subtree push` иногда отказывается пушить, если история разошлась.
> Тогда: `git push amvera-api $(git subtree split --prefix backend main):master --force`

## Что делать, если бэкап отвалился

1. Админка → Бэкапы → открыть лог последнего прогона.
2. Нет места на диске — увеличить постоянный диск в тарифе проекта.
3. Ошибка про версию `pg_dump` — см. **ловушку 4**, это не поломка: дамп
   продолжает делаться логическим способом.
4. Прогнать вручную кнопкой «Полный» и проверить целостность кнопкой
   «Проверить целостность».

## Регулярные операции

| Когда | Что |
|---|---|
| Ежедневно | Убедиться, что бэкап зелёный |
| Еженедельно | Дашборд: мёртвый контент и пустые поисковые запросы → бэклог |
| Ежемесячно | Гайды с истёкшим `reviewAt`; обновления зависимостей |
| Ежеквартально | **Учебное восстановление**; ревизия доступов |

Учебное восстановление — из консоли проекта `pai-api`:

```bash
npm run restore -- --latest --target=check
```

**Бэкап, который ни разу не разворачивали, бэкапом не считается.**

## Второй контур бэкапа: копия вне площадки

Бэкапы на `/data` защищают от потери данных приложением, но не от потери самого
аккаунта Amvera. Если это важно — заведите Google Drive как второй контур.

**Тогда, и только тогда, актуальны три ловушки Google OAuth.** Они полностью
описаны ниже; при `BACKUP_PROVIDER=local-drive` их можно игнорировать.

<details>
<summary><b>Развернуть: настройка Google Drive и три его ловушки</b></summary>

### ⚠️ Ловушка A. Статус приложения — «In production», а не «Testing»

**Где:** [console.cloud.google.com](https://console.cloud.google.com) → APIs & Services →
OAuth consent screen → **PUBLISH APP**.

**Что будет, если забыть:** в статусе *Testing* Google протухает refresh-токен
**ровно через 7 дней**. Бэкапы отвалятся через неделю после запуска — когда все
уже расслабились. При переходе покажут «приложение не проверено» →
«Дополнительно» → «Перейти (небезопасно)»; это нормально для внутреннего приложения.

### ⚠️ Ловушка B. Scope — ровно один: `drive.file`, НЕ `drive`

**Что будет с `drive`:** приложение попадёт в *restricted scope* и потребует платной
верификации Google. `drive.file` даёт доступ только к файлам, созданным самим
приложением, — этого достаточно.

**Следствие:** папку `PAI Backups` **нельзя создать руками** в веб-интерфейсе Диска —
приложению она не будет видна. Её создаёт само приложение при первом прогоне.

### ⚠️ Ловушка C. `access_type=offline` **и** `prompt=consent`

**Что будет без `prompt=consent`:** при повторной авторизации Google вернёт только
access-токен, а refresh — нет, и **это не видно из ответа**. Бэкап проработает час
и встанет. В `npm run drive:auth` оба параметра уже зашиты, и скрипт ругается,
если `refresh_token` не пришёл.

### Настройка

1. Завести **выделенный** Google-аккаунт (не личный чей-то), 2FA, коды в менеджер паролей.
2. Google Cloud → новый проект → включить **Google Drive API**.
3. OAuth consent screen: scope `drive.file` (ловушка B), затем PUBLISH APP (ловушка A).
4. Credentials → OAuth client ID → тип **Desktop app**.
5. Локально получить токен:

   ```bash
   cd backend && npm run drive:auth
   ```

6. В переменные проекта `pai-api` добавить секретами:
   `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN`,
   и переменную `BACKUP_PROVIDER=google-drive`.
7. Проверить тем путём, которым пойдёт прод: `npm run backup -- --kind=DB`.

**Если отвалилось:** в логе прогона `invalid_grant` → Google отозвал доступ.
Причины: смена пароля аккаунта, ручной отзыв в
[Сторонних приложениях](https://myaccount.google.com/permissions), удаление
OAuth-клиента, или **приложение осталось в статусе Testing**. Починка — повторить
`npm run drive:auth` и обновить секрет.

</details>

## Если понадобится CDN и раздача медиа с edge

На Amvera медиа отдаёт сам backend с постоянного диска — для команды до 50 человек
этого достаточно. Cloudflare и R2 нужны, только если появятся жалобы на скорость
из дальних гео или объём видео перерастёт диск.

<details>
<summary><b>Развернуть: Cloudflare + R2</b></summary>

1. Домен делегировать на Cloudflare, поддомены проксировать (оранжевое облако),
   в качестве origin указать адреса Amvera.
2. Cache Rules: `media.*` — Cache Everything, Edge TTL 1 год; `api.*` — Bypass.
3. R2 → бакет `pai-media` → API-токен (Object Read & Write) → custom domain.
4. В переменные `pai-api`: `STORAGE_PROVIDER=r2`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`,
   `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, `R2_ENDPOINT`, `R2_PUBLIC_URL`.
5. Для сброса кэша при публикации: `CDN_PROVIDER=cloudflare`, `CLOUDFLARE_ZONE_ID`,
   `CLOUDFLARE_API_TOKEN` (шаблон токена «Zone.Cache Purge»).

**Код R2 написан, но ни разу не запускался** — проверьте загрузку картинки
и `curl -I` на её адрес: должен прийти AVIF с `cache-control: immutable`.

</details>

## Telegram-уведомления

Не обязательны: без бота алерты пишутся в лог приложения, который виден в Amvera.

<details>
<summary><b>Развернуть: подключение бота</b></summary>

1. [@BotFather](https://t.me/BotFather) → `/newbot` → скопировать токен.
2. Написать боту, открыть `https://api.telegram.org/bot<ТОКЕН>/getUpdates`, взять `chat.id`.
3. В переменные `pai-api`: `TELEGRAM_PROVIDER=telegram`, `TELEGRAM_BOT_TOKEN` (секрет),
   `TELEGRAM_BOT_USERNAME`, `TELEGRAM_ALERT_CHAT_ID`.
4. Для входа через Telegram на сайте: у BotFather `/setdomain` → домен сайта,
   плюс `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` в `web/Dockerfile` (ловушка 1!).

**Вход через Telegram и бот написаны, но вживую не проверялись.**

## Сводка: что переключается одной переменной

| Что | Переменная | Локально | Amvera | Внешний провайдер |
|---|---|---|---|---|
| Хранилище медиа | `STORAGE_PROVIDER` | `local` | `local` (`/data/storage`) | `r2` |
| Бэкап | `BACKUP_PROVIDER` | `local-drive` | `local-drive` (`/data/backups`) | `google-drive` |
| Уведомления | `TELEGRAM_PROVIDER` | `console` | `console` | `telegram` |
| Сброс кэша CDN | `CDN_PROVIDER` | `noop` | `noop` | `cloudflare` |

Код приложения при переключении не меняется. Что именно не проверялось вживую —
в [PROGRESS.md](PROGRESS.md).
