# SETUP.md — развёртывание на Amvera Cloud

Локально система работает **без единого внешнего аккаунта**. Этот документ нужен
только для выкатки в облако.

Всё разворачивается как **одно приложение Amvera плюс управляемый PostgreSQL**.
Порядок шагов важен: каждый следующий опирается на предыдущий.

---

## Что получится

| | |
|---|---|
| Проектов в Amvera | **2**: приложение + база данных |
| Адрес | один на всё: сайт в корне, админка на `/admin/`, API на `/api/` |
| Своё доменное имя | не обязательно, хватит бесплатного `*.amvera.io` |
| Внешние аккаунты | **не нужны**: медиа и бэкапы на постоянном диске Amvera |
| Деплой | `git push origin main` — вебхук GitHub сам запускает пересборку |

Всё три сервиса живут в одном контейнере: nginx разводит запросы между backend,
Next.js и статикой админки. Это не только дешевле трёх проектов — **один origin**
снимает разом три проблемы: кука авторизации работает и на сайте, и в админке;
CORS не нужен; адрес API становится относительным путём и не требует
переменных этапа сборки.

# ⚠️ ШЕСТЬ ЛОВУШЕК AMVERA

**Прочитайте до того, как создавать проекты.**

> ## 1. Переживает пересборку только `/data`. Папка `/app` стирается
>
> Документация прямо предупреждает: файлы вне постоянного диска «будут потеряны»
> при перезагрузке и пересборке.
>
> **Чем бьёт нас:** там лежат все загруженные скриншоты и видео. Если оставить
> хранилище по умолчанию (`./storage` внутри `/app`), всё будет работать ровно
> до первой пересборки, а потом медиа исчезнут — молча, без ошибок.
>
> **Что делать:** обязательно задать `STORAGE_LOCAL_DIR=/data/storage`
> и `BACKUP_LOCAL_DIR=/data/backups` (шаг 4) и включить постоянный диск проекту.
> В проверке на шаге 6 есть отдельный пункт «пересобрать и убедиться, что медиа на месте» —
> не пропускайте его.

> ## 2. Платформа кладёт в контейнер свой `PORT`
>
> Обычно `PORT=80`. Наш backend, как и положено, умеет читать `PORT` — и в общем
> контейнере он попытался бы занять порт, на котором уже сидит nginx.
>
> **Уже решено:** `deploy/supervisord.conf` явно задаёт `PORT=3001` для backend
> и `PORT=3000` для Next.js, перебивая платформенное значение. Знать об этом
> нужно, чтобы не «чинить» это место, увидев два PORT в конфигурации.

> ## 3. У приложений и у базы РАЗНЫЙ формат внутреннего адреса
>
> ```
> приложение:  amvera-<проект>-run-<ник>
> база:        amvera-<ник>-cnpg-<проект>-rw
> ```
>
> Порядок ника и имени проекта переставлен местами. Перепутать — самая частая
> причина «не могу подключиться к базе». Нам нужен только адрес базы:
> внутри одного контейнера сервисы общаются по `127.0.0.1`.
>
> Суффиксы базы: `-rw` — чтение и запись (нужен нам), `-ro` — реплика только
> на чтение, `-r` — любой узел.

> ## 4. Версия `pg_dump` должна совпадать с версией сервера
>
> В образ ставится `postgresql16-client`. Если кластер Amvera окажется новее,
> `pg_dump` откажется работать.
>
> **Молчаливой поломки не будет:** бэкап сам переключится на логический дамп
> средствами Node, и в логе прогона будет видно `method: ndjson`. Если хочется
> именно `pg_dump` — поправьте версию клиента в корневом `Dockerfile`
> под ту, что показана на странице кластера.

> ## 5. Приложение засыпает после 30 дней без активности
>
> У замороженного проекта очищается папка артефактов и отвязываются домены;
> чтобы вернуть — нужна пересборка. Для базы знаний, которой пользуются каждый
> день, это не проблема, но помните об этом, если система постоит без дела.
> Данные на `/data` при этом сохраняются.

> ## 6. Переменные окружения бывают двух этапов — не перепутайте
>
> В окне добавления переменной есть выбор **«Этап: Запуск / Сборка»**.
> Переменная этапа «Запуск» на сборку не попадает, и наоборот.
>
> **Нам нужен только «Запуск».** Адрес API относительный, поэтому вшивать
> его в бандл при сборке не требуется — именно ради этого всё собрано
> в один origin. Если когда-нибудь разнесёте сервисы по разным доменам,
> `NEXT_PUBLIC_API_URL` и `VITE_API_URL` придётся задавать этапом «Сборка».

## Шаг 1. Аккаунт и тариф — 10 минут

1. Зарегистрироваться: [amvera.ru](https://amvera.ru/), пополнить баланс.
2. Запомнить свой ник — он входит во внутренний адрес базы.

Тарифы (цены за месяц):

| План | CPU | RAM | SSD | Цена |
|---|---|---|---|---|
| Начальный | 0.25 | 500 МБ | 5 ГБ | 290 ₽ |
| Начальный Плюс | 0.5 | 1 ГБ | 7 ГБ | 490 ₽ |
| Стандарт | 1 | 2.5 ГБ | 15 ГБ | 1450 ₽ |

**Что брать под приложение.** В контейнере три процесса, плюс обработка картинок
(sharp) и видео (ffmpeg). «Начальный» с 500 МБ не годится — не хватит памяти
на сборку вариантов. Минимум — **Начальный Плюс**, комфортно — **Стандарт**,
особенно если будете грузить видео.

**Под базу** достаточно «Начального» (290 ₽).

**Итого:** 780 ₽/мес по минимуму, ~1740 ₽/мес комфортно.
Сверх тарифа диск считается по 35 ₽ за ГБ — учитывайте под видео.

> Сборка идёт в отдельном контейнере и тарифицируется так же, как приложение.
> Это разовые минуты на каждый деплой, но в счёте они видны.

## Шаг 2. База данных — 15 минут

1. На главной: **PostgreSQL** → «Создать базу данных».
2. Название `pai-db`, тариф «Начальный».
3. Заполнить:
   - имя базы: `pai`
   - пользователь: `pai` (имя `postgres` занято платформой)
   - пароль: длинный, сразу в менеджер паролей
   - реплик: 1
4. Дождаться статуса «PostgreSQL запущен».
5. Со страницы кластера взять внутренний адрес (**ловушка 3**) и собрать строку:

   ```
   postgresql://pai:<пароль>@amvera-<ваш-ник>-cnpg-pai-db-rw:5432/pai
   ```

Наружу база не смотрит — так и надо. Для доступа DBeaver'ом на странице кластера
отдельно создаётся домен типа POSTGRES с SSL.

## Шаг 3. Создать приложение — 5 минут

1. «Создать проект» → тип **Приложение**, окружение **Docker**.
2. Имя: `pai`. Тариф — не ниже «Начальный Плюс» (**шаг 1**).
3. Включить **постоянный диск** (**ловушка 1**).

Порт и точка монтирования уже описаны в `amvera.yml` в корне репозитория —
править ничего не нужно:

```yaml
run:
  persistenceMount: /data
  containerPort: "80"
```

Форма файла сверена с генератором [manifest.amvera.ru](https://manifest.amvera.ru):
`containerPort` там задаётся **строкой**, а не числом.

## Шаг 4. Переменные окружения — 15 минут

Раздел **«Переменные»** проекта `pai`. Этап — **«Запуск»** (**ловушка 6**).
Пароли и токены добавляйте как **секреты**: они хранятся в отдельном хранилище,
а не в базе платформы.

Сначала сгенерируйте два секрета — по 32 случайных байта в hex.
Выполните дважды: первый результат в `JWT_SECRET`, второй в `REVALIDATE_SECRET`.

**Через Node** (он у вас уже стоит — на нём работает проект). Годится в любой
консоли: PowerShell, cmd, Git Bash, терминал macOS и Linux:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

**Чистый PowerShell**, если Node под рукой нет:

```powershell
$b = New-Object 'System.Byte[]' 32; [System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); ($b | ForEach-Object { $_.ToString('x2') }) -join ''
```

> В PowerShell **нет** `openssl` — он ставится вместе с Git и доступен только
> в Git Bash. Если привыкли к `openssl rand -hex 32`, запускайте его оттуда.
> Не берите `Get-Random`: это не криптографический генератор, для секретов
> он не годится.

| Переменная | Значение | Тип |
|---|---|---|
| `DATABASE_URL` | строка подключения из шага 2 | секрет |
| `JWT_SECRET` | первый сгенерированный | секрет |
| `REVALIDATE_SECRET` | второй сгенерированный | секрет |
| `ADMIN_PASSWORD` | нормальный пароль, не `admin12345` | секрет |
| `NODE_ENV` | `production` | переменная |
| `ADMIN_LOGIN` | ваш логин | переменная |
| `ADMIN_NAME` | ваше имя | переменная |
| `COOKIE_SECURE` | `true` | переменная |
| `STORAGE_LOCAL_DIR` | `/data/storage` | переменная |
| `BACKUP_LOCAL_DIR` | `/data/backups` | переменная |
| `STORAGE_LOCAL_PUBLIC_URL` | `https://pai-<ник>.amvera.io/media` | переменная |
| `PUBLIC_WEB_URL` | `https://pai-<ник>.amvera.io` | переменная |
| `PUBLIC_ADMIN_URL` | `https://pai-<ник>.amvera.io/admin` | переменная |

> **Следите за лишними пробелами при вставке значений.** Копирование из таблицы
> или терминала легко приносит с собой пробел или табуляцию. Приложение теперь
> само обрезает значения, но проверить стоит: раздел «Бэкапы» в админке показывает
> реальные пути после разбора и подсвечивает жёлтым, если путь не абсолютный.

Чего задавать **не нужно**: `COOKIE_DOMAIN` (один origin — кука host-only),
`CORS_ORIGINS` (кросс-доменных запросов нет), `PORT`, `WEB_INTERNAL_URL`
и `API_INTERNAL_URL` — они заданы внутри образа.

> `STORAGE_LOCAL_PUBLIC_URL` можно оставить относительным (`/media`) — в браузере
> работает одинаково. Абсолютный адрес лучше тем, что попадает в экспортируемый
> Markdown бэкапа: такие ссылки открываются и без работающего сайта.

## Шаг 5. Деплой — 15 минут

Есть два способа. **Связка с GitHub удобнее**: код остаётся в привычном
репозитории, а деплой происходит сам по пушу.

### Вариант А (рекомендуется): пуш в GitHub запускает пересборку

1. В проекте Amvera: вкладка **«Репозиторий»** → выбрать **GitHub**.
2. Тип события — **push**.
3. Придумать **секрет** (потом значение скрывается — сохраните его).
4. Указать ветку удалённого репозитория: `main`.
5. Скопировать сгенерированный **URL вебхука**, нажать «Применить».
6. В GitHub: Settings → Webhooks → Add webhook:
   - **Payload URL** — скопированный из Amvera,
   - **Content type** — `application/json`,
   - **Secret** — тот же, что задали в Amvera,
   - события — **Just the push event**.
7. Сохранить.

Всё. Дальше обычный `git push origin main` сам запускает пересборку и деплой.

> Ограничения: вебхук реагирует **только на push**; к одному репозиторию Amvera
> можно привязать один хук. Для приватного репозитория дополнительно нужен
> personal access token с правами `repo`. При обновлении Amvera тянет изменения
> стратегией слияния «their» — то есть побеждает то, что пришло из GitHub.

### Вариант Б: пуш напрямую в репозиторий Amvera

Годится для первого деплоя или если вебхук не настраивали:

```bash
git remote add amvera https://git.amvera.ru/<ваш-ник>/pai
git push amvera main:master
```

Amvera собирает из ветки `master`, поэтому локальная `main` пушится как `main:master`.
Логин и пароль — от аккаунта Amvera.

### В обоих случаях

Сборка стартует сама. Следить: вкладки **«Лог сборки»** и **«Лог приложения»**.
Первая сборка занимает 5–10 минут: собираются backend, Next.js и админка.

При старте контейнер сам накатывает миграции и создаёт администратора —
в логе приложения это видно как `[start] применяю миграции`.

> ## ⚠️ С вебхуком пуш = выкатка в прод
>
> Пуш в `main` перестаёт быть просто отправкой кода. Отсюда два следствия:
>
> 1. **Не пушьте полуготовое** — оно немедленно уедет на боевой сайт.
> 2. **Проверяйте сборку до пуша, и именно из выгрузки git**, а не из рабочей
>    папки. Локальная сборка не видит файлов, не попавших в репозиторий:
>
>    ```bash
>    rm -rf /tmp/clean && mkdir -p /tmp/clean
>    git archive HEAD | tar -x -C /tmp/clean
>    cd /tmp/clean && docker build -t pai-clean .
>    ```
>
>    Именно так был пойман пропуск целой папки `backend/src/services/storage`,
>    которую вычеркнул шаблон в `.gitignore`. На сборке Amvera это выглядело как
>    `Cannot find module './storage/index.js'`, а локально всё собиралось.

> Файлы из `.gitignore` до сборки не доезжают. Это правильно: `.env`, `storage/`
> и `backups/` остаются локальными.

## Шаг 6. Проверка — 15 минут

Адрес: `https://pai-<ник>.amvera.io` (включается в «Настройках» проекта).

- [ ] `/health` → `{"ok":true,"db":true,"storage":true}`
- [ ] Без входа сайт уводит на `/login`
- [ ] Вход по `ADMIN_LOGIN` / `ADMIN_PASSWORD` работает
- [ ] `/admin/` открывается, и та же сессия действует — второй раз входить не нужно
- [ ] Загрузка картинки доходит до статуса READY, вариантов больше одного
- [ ] **Пересобрать проект и убедиться, что картинка на месте** ← главная проверка
      постоянного диска (**ловушка 1**). Если её пропустить, пропажу медиа
      обнаружите через недели
- [ ] Публикация гайда → он виден на публичном сайте
- [ ] «Бэкапы» → «Полный» отрабатывает зелёным
- [ ] В логе прогона видно способ дампа: `pg_dump` или `ndjson` (**ловушка 4**)

## Шаг 7. Своё доменное имя — по желанию

Бесплатного `pai-<ник>.amvera.io` достаточно: всё на одном origin, кука работает.

Свой домен нужен, если хочется красивого адреса:

1. «Настройки» проекта → «Добавить домен».
2. Прописать у регистратора DNS-записи, которые покажет Amvera.
3. Дождаться сертификата — Amvera выпускает его сама.
4. Обновить `STORAGE_LOCAL_PUBLIC_URL`, `PUBLIC_WEB_URL`, `PUBLIC_ADMIN_URL`.

Ничего другого менять не придётся: адреса внутри приложения относительные.

## Эксплуатация

### Обновление

С настроенным вебхуком (вариант А) — обычный пуш, пересборка запустится сама:

```bash
git push origin main
```

Без вебхука — напрямую в Amvera:

```bash
git push amvera main:master
```

### Если что-то не поднялось

1. «Лог сборки» — ошибки компиляции.
2. «Лог приложения» — старт контейнера. Ищите строки `[start]`, `[api] слушаю`,
   `[jobs] очередь pg-boss запущена`.
3. Приложение перезапускается само; если не держится дольше минуты — статус
   «Ошибка приложения», а после 30 минут попыток на первом деплое —
   «Остановлено из-за повторяющейся ошибки».

### Регулярные операции

| Когда | Что |
|---|---|
| Ежедневно | Убедиться, что бэкап зелёный |
| Еженедельно | Дашборд: мёртвый контент и пустые поисковые запросы → бэклог |
| Ежемесячно | Гайды с истёкшим `reviewAt`; обновления зависимостей |
| Ежеквартально | **Учебное восстановление**; ревизия доступов |

Учебное восстановление — из консоли проекта:

```bash
cd /app/backend && node dist/scripts/restore.js --latest --target=check
```

**Бэкап, который ни разу не разворачивали, бэкапом не считается.**

### Что бэкапит сама Amvera

Платформа хранит копии `/data` за последние двое суток (тариф «Начальный Плюс»
и выше). Это дополнение к нашим бэкапам, а не замена: у нас ретеншен
7 дней × 4 недели × 6 месяцев и проверяемое восстановление.

## Приложение А. Копия бэкапов вне площадки

Бэкапы на `/data` защищают от сбоя приложения, но не от потери аккаунта Amvera.
Если это важно — подключите Google Drive вторым контуром.

**Только здесь становятся актуальны три ловушки Google OAuth.**
При `BACKUP_PROVIDER=local-drive` их можно игнорировать.

<details>
<summary><b>Развернуть: Google Drive и три его ловушки</b></summary>

### ⚠️ A. Статус приложения — «In production», а не «Testing»

[console.cloud.google.com](https://console.cloud.google.com) → APIs & Services →
OAuth consent screen → **PUBLISH APP**.

**Если забыть:** в статусе *Testing* refresh-токен протухает **ровно через 7 дней**.
Бэкапы отвалятся через неделю после запуска — когда все расслабились.
При переходе покажут «приложение не проверено» → «Дополнительно» →
«Перейти (небезопасно)»; для внутреннего приложения это нормально.

### ⚠️ B. Scope — ровно один: `drive.file`, НЕ `drive`

**Если взять `drive`:** приложение попадёт в *restricted scope* и потребует
платной верификации Google. `drive.file` даёт доступ только к файлам, созданным
самим приложением, — этого достаточно.

**Следствие:** папку `PAI Backups` **нельзя создать руками** в веб-интерфейсе
Диска — приложению она не будет видна. Её создаёт само приложение.

### ⚠️ C. `access_type=offline` **и** `prompt=consent`

**Если забыть `prompt=consent`:** при повторной авторизации Google вернёт только
access-токен, а refresh — нет, и **это не видно из ответа**. Бэкап проработает
час и встанет. В `npm run drive:auth` оба параметра зашиты, и скрипт ругается,
если `refresh_token` не пришёл.

### Настройка

1. Завести **выделенный** Google-аккаунт (не личный), 2FA, коды в менеджер паролей.
2. Google Cloud → проект → включить **Google Drive API**.
3. OAuth consent screen: scope `drive.file` (B), затем PUBLISH APP (A).
4. Credentials → OAuth client ID → тип **Desktop app**.
5. Локально: `cd backend && npm run drive:auth`.
6. В переменные проекта секретами: `GOOGLE_OAUTH_CLIENT_ID`,
   `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN`;
   переменной: `BACKUP_PROVIDER=google-drive`.

**Если отвалилось:** в логе прогона `invalid_grant` — Google отозвал доступ.
Причины: смена пароля аккаунта, ручной отзыв в
[Сторонних приложениях](https://myaccount.google.com/permissions), удаление
OAuth-клиента, **или приложение осталось в статусе Testing**.
Починка: повторить `npm run drive:auth`, обновить секрет, перезапустить.

</details>

## Приложение Б. CDN и раздача медиа с edge

Медиа отдаёт nginx внутри контейнера с постоянного диска — для команды
до 50 человек этого достаточно. Cloudflare и R2 нужны, только если появятся
жалобы на скорость из дальних гео или объём видео перерастёт диск.

<details>
<summary><b>Развернуть: Cloudflare + R2</b></summary>

1. Домен делегировать на Cloudflare, origin — адрес приложения в Amvera.
2. Cache Rules: `/media/*` — Cache Everything, Edge TTL 1 год; `/api/*` — Bypass.
3. R2 → бакет `pai-media` → API-токен (Object Read & Write) → custom domain.
4. В переменные: `STORAGE_PROVIDER=r2`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`,
   `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, `R2_ENDPOINT`, `R2_PUBLIC_URL`.
5. Для сброса кэша при публикации: `CDN_PROVIDER=cloudflare`,
   `CLOUDFLARE_ZONE_ID`, `CLOUDFLARE_API_TOKEN` (шаблон «Zone.Cache Purge»).

**Код R2 написан, но ни разу не запускался.** После переключения проверьте
загрузку картинки и `curl -I` на её адрес: должен прийти AVIF с `immutable`.

</details>

## Приложение В. Telegram-уведомления

Не обязательны: без бота алерты пишутся в лог приложения, видный в Amvera.

<details>

4. Для входа через Telegram на сайте: у BotFather `/setdomain` → ваш домен.
   `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` — переменная **этапа «Сборка»**
   (**ловушка 6**), потому что она вшивается в бандл.

## Сводка: что переключается одной переменной

| Что | Переменная | Локально | Amvera | Внешний провайдер |
|---|---|---|---|---|
| Хранилище медиа | `STORAGE_PROVIDER` | `local` | `local` (`/data/storage`) | `r2` |
| Бэкап | `BACKUP_PROVIDER` | `local-drive` | `local-drive` (`/data/backups`) | `google-drive` |
| Уведомления | `TELEGRAM_PROVIDER` | `console` | `console` | `telegram` |
| Сброс кэша CDN | `CDN_PROVIDER` | `noop` | `noop` | `cloudflare` |

Код приложения при переключении не меняется. Что именно не проверялось
вживую — в [PROGRESS.md](PROGRESS.md).
