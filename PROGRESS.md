## Этап 3. Медиа-подсистема — ✅

Сделано:

- **`StorageProvider`** (§3.1) с методами `presignPut / put / get / getBuffer / exists /
  delete / publicUrl / list`.
  - `local.provider.ts` — папка на диске. Тоже выдаёт presigned-ссылку (HMAC + TTL 15 мин),
    указывающую на сам backend: клиентский путь загрузки не отличается от R2.
  - `r2.provider.ts` — 🟡 написан на `@aws-sdk/client-s3`, не запускался. Тот же код
    подходит для MinIO и Backblaze B2.
- **Загрузка напрямую в хранилище, минуя backend** (§3.2): presign → `PUT` из браузера
  через `XMLHttpRequest` с прогрессом → `complete` → задача в очередь.
- **Дедупликация по sha256**: браузер считает хеш до загрузки; если такой файл уже есть,
  сервер возвращает существующий `Media` и загрузка не происходит вовсе.
- **Обработка картинок** (sharp): автоповорот по EXIF, метаданные вырезаются,
  ширины 320/640/960/1280/1920 (без апскейла) × AVIF + WebP, blurhash.
  Ключи вида `img/<sha8>/<width>.avif` — content-hash, поэтому кэш `immutable`.
- **Видео** (§3.4): ffprobe → длительность и размеры, постер на 10% длительности,
  `variants` сразу массивом рендишнов (лестница качеств этапа 7 ляжет без миграции).
  Без ffmpeg видео сохраняется и играет, а причина отсутствия постера видна в админке.
- **Очередь pg-boss** поверх того же Postgres. Если очередь не поднялась, задачи
  выполняются прямо в процессе — обработка не встаёт молча.
- **Медиа-библиотека в админке**: сетка с превью, вкладки по типу, поиск,
  drag-and-drop и выбор файлов, прогресс по стадиям (хеш → загрузка → обработка),
  карточка файла (варианты, alt, «где используется»), удаление с проверкой ссылок.

Проверено запуском (полный цикл через curl):

| Проверка | Результат |
|---|---|
| Загрузка PNG 1600×900 | READY за ~2 с, 8 вариантов (AVIF+WebP × 4 ширины), blurhash есть |
| 1920px-вариант у картинки шириной 1600 | не создан — апскейла нет |
| `curl -I` на вариант | `cache-control: public, max-age=31536000, immutable`, `content-type: image/avif` |
| Повторный presign того же файла | `deduplicated: true`, загрузка не потребовалась |
| Подделанная подпись в ссылке загрузки | 403 |
| Видео без ffmpeg | READY, играет (`206 Partial Content` на Range), причина отсутствия постера видна в UI |
| Удаление используемого файла | 409 со списком гайдов |

**Замечание по sha256 в браузере.** План говорит «стримом», реализовано через
`crypto.subtle.digest` по файлу целиком: у SubtleCrypto нет потокового API, а своя
реализация SHA-256 в бандле ради редких больших видео не окупается (скриншоты —
единицы мегабайт). Для файла в сотни мегабайт шаг заметен по времени, поэтому в UI
показывается стадия «считаю хеш».

## Этап 5. Публичный сайт — ✅

Backend — публичное чтение (`routes/public.ts`):

- `GET /categories` — дерево со счётчиками только опубликованных гайдов.
- `GET /guides` — карточки с фильтрами (категория, тег, уровень, закреплённые, «с даты»).
- `GET /guides/:slug` — документ + справочник медиа + связанные гайды + оглавление.
  Отдаём **документ и медиа отдельно, а не готовый HTML**: рендерер на сайте сам
  собирает `<picture srcset>`, иначе управление скоростью теряется.
- `GET /guides/required/mine`, `GET /me/progress`, `GET/PUT /guides/:id/progress`,
  `POST /guides/:id/feedback` — персональное, всегда без кэша.
- `GET /search` — Postgres FTS: `websearch_to_tsquery` (не падает на кривом вводе),
  `ts_rank`, подсветка через `ts_headline`; каждый запрос пишется в `SearchQuery`.
- `GET /search/suggest` — триграммные подсказки при пустой выдаче.

**Как публичный контент попадает в ISR-кэш.** Кэшируемые страницы ходят в API
с внутренним токеном вместо cookie — иначе кэш стал бы персональным. Безопасно это
ровно потому, что `web` сам никого не пускает: middleware проверяет **подпись** JWT
(`jose`) до отдачи страницы. Проверено: подделанная кука даёт редирект на `/login`.

Сайт (Next.js 15, App Router):

| Маршрут | Режим | Что показывает |
|---|---|---|
| `/` | динамический (персональный блок) | обязательное со статусом, закреплённое, новое за неделю, разделы |
| `/c/[category]` | SSG + ISR 1 ч | карточки, фильтры по уровню и тегам |
| `/g/[slug]` | SSG + ISR 1 ч | гайд, оглавление-sticky, «полезно?», связанные |
| `/search` | динамический | результаты с подсветкой, подсказки при нуле |
| `/me` | динамический | прочитано, время за чтением, обязательное, продолжить |
| `/login`, `/invite` | статические | вход и активация кода |

- **Собственный рендерер `JSON → React`** (`components/GuideContent.tsx`):
  `<picture>` c AVIF/WebP `srcset`, явные `width`/`height` (нет CLS),
  `loading="lazy"` кроме первой картинки, у неё — `fetchpriority="high"`;
  таблицы скроллятся внутри себя на мобильных; внешние ссылки с `rel="noopener"`.
- **Клиентских кусков ровно четыре**, как требует §3.1: чеклист, видеоплеер,
  поиск и сборщик аналитики. Ни один `useEffect` не грузит сам гайд.
- **Ленивый видеоплеер**: до клика на странице только постер и кнопка. После клика —
  скорость 0.75×–2×, запоминание позиции, трекинг порогов 25/50/75/95.
- **Чеклист** сохраняет состояние в localStorage (мгновенно) и на сервере (между устройствами).
- **On-demand ревалидация** `POST /api/revalidate` с секретом; дёргается при публикации.
- `noindex` в `<meta>` и в заголовке `X-Robots-Tag`, `robots.txt` — `Disallow: /`.

**Сборщик аналитики (§8.1) написан здесь, а не в этапе 8** — чеклист и плеер этапа 5
это ровно те компоненты, которые шлют события, и без сборщика их пришлось бы
переписывать. Приём событий, роллапы и дашборд — этап 8.

решение, а не деталь реализации. Замеры Lighthouse и LCP из удалённых гео не
проводились: нет прода за CDN.

    multipart и **resumable** upload для файлов > 5 МБ, `files.delete` вместо корзины,
    экспоненциальный бэкофф на `rateLimitExceeded`, `about.get` для остатка места.
  - `drive-auth.ts` — 🟡 OAuth2 из §9.0 дословно: `setCredentials`, обработчик
    `tokens` для сохранения ротированного refresh-токена, чтение токена
    «сначала БД, потом .env», громкий алерт на `invalid_grant`.
- **Инкрементальность по sha256** (§9.3): у медиа хеш берётся из БД и файл вообще
  не читается, если он не менялся; изменённое грузится, после загрузки сверяется
  контрольная сумма — защита от «залилось битым».
- **Формат хранения** — точно как в §9.2: `content/<slug>/{meta,guide.json,guide.md,media.json}`,
  `content/_index.json`, `media/…` зеркалом бакета, `db/<дата>/dump.*.gz`,
  `manifests/<дата>/manifest-N.json` и указатель `manifest-latest.json`.
  Markdown — сознательно: при полном отказе платформы гайды читаются глазами.
- **Удалённые объекты не удаляются сразу**: помечаются и чистятся через
  `BACKUP_TOMBSTONE_DAYS` (30) — защита от «админ снёс гайд, бэкап повторил».
- **Ретеншен дампов** 7 дней × 4 недели × 6 месяцев.
- **Дамп БД — три стратегии** (DECISIONS §4): `pg_dump` из PATH → `pg_dump` внутри
  docker-контейнера → логический NDJSON-дамп на Node. Восстановление определяет
  формат само (по сигнатуре `PGDMP`) и двигает последовательности после вставки.
- **Расписание** (§9.4) через pg-boss: контент раз в час, медиа раз в час,
  дамп БД в 04:00, полная сверка в воскресенье 05:00, плюс ежечасный сторож,
  который бьёт тревогу, если успешного бэкапа не было дольше порога.
- **Восстановление** — `npm run restore` с тремя режимами: `check` (ничего не меняет,
  можно гонять хоть каждый день), `media`, `full` (требует явного `--yes`).
  Проверяет версию схемы, хеши всех объектов, резолвинг всех `mediaId`
  у опубликованных гайдов и наличие всех ключей в хранилище; печатает отчёт с временем.
- **Экран в админке**: транспорт, «последний успешный N часов назад» с баннером
  при превышении порога, объём, место на аккаунте, кнопки прогонов, проверка
  целостности с отчётом, возврат недостающих медиафайлов, логи прогонов.
  Полное восстановление БД в интерфейс намеренно не выведено — операция
  разрушительная, ей место в консоли с явным флагом.

## Проверка сборки из чистой выгрузки

Сборка на Amvera идёт не из рабочей папки, а из склонированного репозитория,
и файлы под `.gitignore` до неё не доезжают. Локальная сборка это не ловит:
на диске лежит всё, включая неотслеживаемое.

Поэтому перед выкаткой сборку нужно проверять на том, что реально в git:

```bash
rm -rf /tmp/clean && mkdir -p /tmp/clean
git archive HEAD | tar -x -C /tmp/clean
cd /tmp/clean && docker build -t pai-clean .
```

Этой проверкой был найден пропуск трёх файлов провайдеров хранилища —
см. DECISIONS §13.

**Две вещи, найденные на финальной сверке и исправленные:**

1. Middleware пропускал на страницу при живом refresh-токене, но серверный рендер
   в этот момент видел протухший access и показывал человека гостем — без блока
   «обязательно к прочтению» и с надписью «База знаний» вместо имени.
   Добавлен `SessionRefresher`: рендерится только когда сервер не опознал
   пользователя, один раз обновляет пару токенов и перерисовывает страницу.
2. `seed:demo` писал гайды прямо в базу, минуя API, поэтому ISR-кэш о них не знал
   и счётчики категорий висели старыми до часа. Скрипт теперь сам зовёт ревалидацию.
