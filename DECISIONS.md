# DECISIONS.md — самостоятельно принятые решения

План оставляет часть развилок открытыми. Здесь — что выбрано, почему, и что поменять,
когда появятся реальные доступы. Формат: **решение → обоснование → как откатить/поменять**.

Записи добавляются по ходу этапов, сверху — самые общие.

---

## 0. Сквозное: «внешних доступов нет» как требование к архитектуре

**Решение.** Каждый внешний сервис спрятан за интерфейсом с двумя реализациями:
полноценной локальной (работает по умолчанию) и «боевой» (написана, но не запускалась).
Переключение — одной переменной в `.env`, код приложения не трогается.

| Точка | Интерфейс | Локально | Прод |
|---|---|---|---|
| Медиа | `StorageProvider` | `local.provider.ts` (папка `./storage`) | `r2.provider.ts` |
| Бэкап | `BackupTransport` | `local-drive.provider.ts` (папка `./backups`) | `google-drive.provider.ts` |
| Уведомления | `Notifier` | `console.provider.ts` | `telegram.provider.ts` |
| CDN | `CdnProvider` | `noop.provider.ts` | `cloudflare.provider.ts` |

**Обоснование.** Так локальная реализация — не заглушка, а рабочий режим. Вся бизнес-логика
(инкрементальность бэкапа, дедупликация медиа, ретеншен, восстановление) живёт над интерфейсом
и одинакова в обоих режимах. Отличается только транспорт — значит, переключение на прод
не может «внезапно не заработать» из-за неоттестированной логики.

**Что проверено вживую:** локальные реализации — целиком.
**Что написано, но не запускалось:** `r2.provider.ts`, `google-drive.provider.ts`,
`telegram.provider.ts`, `cloudflare.provider.ts`, вход через Telegram. Помечено в PROGRESS.md.

## 1. Версии стека — ровно те, что в плане

**Решение.** Fastify 4.29, Prisma 5.22, Next.js 15.5, React 18 (admin) / 19 (web), pg-boss 9.

**Обоснование.** План фиксирует мажорные версии (§3). На момент разработки существуют
более новые (Next 16, Prisma 7), но переход на них — это отдельное решение с миграцией
API, а не деталь реализации. План — источник истины.

**Когда менять:** отдельной задачей, после того как MVP заработал.

## 2. Транспорт JWT: httpOnly-cookie + Bearer как запасной путь

**Решение.** Access-токен живёт в httpOnly + SameSite=Lax cookie (как требует §5).
`requireAuth` дополнительно принимает заголовок `Authorization: Bearer`.

**Обоснование.** Cookie — основной путь: с ней работают и админка (`withCredentials`),
и middleware Next.js (читает куку до отдачи страницы). Bearer оставлен, потому что без него
невозможно ни отладить API через `curl`, ни написать e2e-тест, ни сходить в API из скрипта.

**Почему на localhost это работает.** `localhost:3000`, `:5173` и `:3001` — разные origin,
но один и тот же site (порт в понятие site не входит), поэтому SameSite=Lax куку браузер
шлёт. На проде поддомены закрываются одной кукой через `COOKIE_DOMAIN=.pai.1sx.biz`.

## 3. Google Drive: `google-auth-library` + REST вместо пакета `googleapis`

**Решение.** OAuth2-клиент берём из `google-auth-library`, а четыре нужных вызова Drive API
(`files.create`, `files.update`, `files.list`, `files.delete`, `about.get`) делаем обычным
`fetch` по REST v3.

**Обоснование.** Код §9.0 плана — `new google.auth.OAuth2(...)`, `oauth.setCredentials(...)`,
`oauth.on('tokens', ...)` — это API именно `google-auth-library`; пакет `googleapis` его
лишь реэкспортирует. При этом `googleapis` разворачивается в ~130 МБ (он содержит клиенты
для всех ~400 API Google), а нам нужен один. Для зависимости, которая в локальном режиме
вообще не выполняется, это неоправданный вес в установке на «чистой машине».

Семантика сохранена дословно, включая обработку ротации refresh-токена и `invalid_grant`.

**Как поменять:** если понадобится именно `googleapis` — заменить импорт в
`services/backup/drive-auth.ts`, остальной код не меняется.

## 4. Дамп БД: три стратегии с автоопределением

**Решение.** `services/backup/db-dump.ts` пытается по очереди:
1. `pg_dump` из `PATH`;
2. `docker exec <PGDUMP_DOCKER_CONTAINER> pg_dump` (контейнер задаётся в `.env`);
3. логический дамп на самом Node: все таблицы → NDJSON, gzip.

**Обоснование.** План говорит `pg_dump -Fc | gzip`. Но критерий готовности — «на чистой
машине, где есть только Docker и Node». На такой машине `pg_dump` в PATH обычно нет:
Postgres живёт в контейнере. Вариант (2) закрывает этот случай, вариант (3) — гарантия,
что бэкап БД делается всегда, даже без Docker.

Восстановление умеет читать оба формата и само определяет, какой перед ним.

**Ограничение варианта (3):** он не переносит расширения и служебные объекты Postgres —
только данные из таблиц Prisma. Схему при восстановлении накатывает `prisma migrate deploy`.
Для нашей БД (весь смысл — в данных) этого достаточно; на проде всё равно отработает (1) или (2).

## 5. Полнотекстовый поиск: SQL-патчи вместо колонки в схеме Prisma

**Решение.** `tsvector`-колонка, GIN-индекс и расширение `pg_trgm` создаются идемпотентными
SQL-патчами из `prisma/sql/*.sql`, которые применяются при старте backend и в `seed`.

**Обоснование.** Prisma 5 не умеет генерируемые колонки. Объявить `Unsupported("tsvector")`
в схеме — значит получить `ADD COLUMN` без выражения `GENERATED ALWAYS AS`, то есть колонку,
которая никогда не заполнится. Патчи написаны как `IF NOT EXISTS`, поэтому применяются
сколько угодно раз, а `prisma migrate deploy` (единственный режим на проде и на чистой
машине) drift не проверяет и на них не ругается.

## 6. Загрузка медиа: presigned PUT одинаково в обоих режимах

**Решение.** `local.provider` тоже отдаёт presigned-URL — только указывающий на сам backend
(`PUT /api/upload/local/:key?token=...`, HMAC-подпись + TTL 15 минут). Браузер в обоих
режимах делает ровно один и тот же `XMLHttpRequest.upload` напрямую по выданному URL.

**Обоснование.** Если бы локальный режим грузил файл «через обычный API-роут», а прод —
presigned-ссылкой в R2, то весь клиентский код загрузки (прогресс, докачка, дедупликация
по sha256) на проде выполнялся бы впервые. Это ровно та ошибка, из-за которой переключение
на прод «внезапно не работает». Здесь путь один и тот же, отличается только хост в URL.

## 7. ffmpeg — необязательная зависимость

**Решение.** Если `ffmpeg`/`ffprobe` не найдены, видео всё равно загружается, сохраняется
и проигрывается: пропускаются только нормализация битрейта и генерация постера.
Медиа получает статус `READY`, а в `Media.error` пишется пояснение, которое видно в админке.

**Обоснование.** Критерий готовности — «на чистой машине есть только Docker и Node».
Требовать ffmpeg значило бы не выполнить его. В Docker-образе backend ffmpeg установлен,
поэтому на проде обработка работает всегда.

**Уточнено после первой загрузки настоящих видео.** Без постеров видеогайд выглядит
серым прямоугольником — то есть «работает» и «пригодно к использованию» здесь
расходятся. Поэтому добавлены `ffmpeg-static` и `ffprobe-static` в
**`optionalDependencies`**, а `services/video.ts` ищет бинарник по порядку:
`FFMPEG_PATH` из `.env` → `ffmpeg` в `PATH` → пакет, если он поставился.

Почему именно `optionalDependencies`: на чистой машине бинарник скачивается сам
и видео обрабатывается из коробки, но если скачать не вышло (нет сети, экзотическая
платформа), `npm install` не падает — система просто продолжает работать без постеров.
Обязательной зависимостью делать нельзя: это ~80 МБ, которые не нужны тому,
у кого ffmpeg уже стоит.

## 8. Аутентификация: три пути, приоритет у логина с паролем

**Решение.** Вход по логину/паролю реализован и проверен end-to-end. Telegram-вход
(Login Widget + одноразовая ссылка от бота) написан по образцу `polina-crm/backend/src/auth.ts`,
но вживую не проверялся — нет бота. Инвайт-коды работают полностью.

**Обоснование.** Прямое требование задачи. Валидация `initData` перенесена дословно
и покрыта юнит-тестом на известном векторе, так что «написано, но не запускалось»
здесь означает «не проверено с настоящим Telegram», а не «не проверено вообще».

## 9. Партиционирование `Event` — не делаем сейчас

**Решение.** Таблица `Event` создана обычной. Партиционирование по месяцам (§8.4) не сделано.

**Обоснование.** Сам план говорит: «при 100 пользователях это ~2–5 млн событий в год:
Postgres справится и без партиций». Конвертация непустой таблицы в партиционированную —
это отдельная миграция с переливкой данных, а не строчка в схеме, и делать её вслепую,
не имея ни одного реального события, — значит потратить время на то, что придётся
переписать по факту. Ретеншен сырых событий (180 дней) реализован и держит объём в узде.

**Когда вернуться:** когда `SELECT count(*) FROM "Event"` перевалит за ~20 млн или
роллап начнёт идти дольше минуты.

## 10. Слэш-меню в редакторе — без пакета `@tiptap/suggestion`

**Решение.** Меню блоков по «/» реализовано напрямую: если текущий абзац начинается
с «/» и не содержит пробела, показываем список у координат курсора
(`editor.view.coordsAtPos`), фильтруем по набранному, вставляем блок и удаляем
набранный текст.

**Обоснование.** `@tiptap/suggestion` — это плагин ProseMirror с собственным
жизненным циклом рендера, который тянет за собой `tippy.js` и требует императивного
моста между ProseMirror и React. Здесь нужен один сценарий из всех, что он умеет,
а поведение (стрелки, Enter, Escape, фильтр) занимает те же тридцать строк.
Меньше слоёв — меньше мест, где меню может «залипнуть» при потере фокуса.

**Побочный эффект:** то же самое меню используется кнопкой «+ Вставить блок» в тулбаре —
один список `INSERT_ITEMS` на оба входа, поэтому они не могут разъехаться.

## 11. Откат версии идёт в черновик, а не в публикацию

**Решение.** `POST /admin/guides/:id/revert/:v` кладёт содержимое версии в
`contentDraft`. Чтобы оно стало видно команде, редактор должен нажать «Опубликовать».

**Обоснование.** План требует «откат в один клик» (§4.2), но откат вслепую прямо
в опубликованное — это способ сломать живой гайд, не увидев, что именно откатываешь.
Один клик остался: после отката содержимое сразу в редакторе, и его видно.
